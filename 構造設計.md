できます。むしろ**制御サーバーのトレースからトラブル要因を切り分ける用途は、Laya/NanoJevの「生成AI」的な使い方より、Jev型のDecision Engineが活きる領域**です。

重要なのは、AIに「ログを読んで原因を文章で答えさせる」のではなく、

> **トレース → 構造化 → 候補原因生成 → 各候補を確率評価 → 時系列・依存関係で絞り込み → 人間に提示**

という構造にすることです。

Layaは `choice / score / noul` を構造化された確率として返せるため、この用途にかなり素直に適用できます。([GitHub][1])

# 1. 想定するシステム

例えば制御サーバーで、

```text
Operator
   ↓
HMI
   ↓
Control Server
   ├─ Task A
   ├─ Task B
   ├─ Task C
   ├─ Middleware
   ├─ PLC communication
   ├─ DB
   └─ Message/Event
```

が動いているとします。

トラブル時には、

```text
10:31:02.001  REQ_START
10:31:02.010  TaskA START
10:31:02.013  MSG_SEND
10:31:02.015  TaskB START
10:31:02.021  PLC_WRITE
10:31:02.025  PLC_TIMEOUT
10:31:02.030  TaskB ERROR
10:31:02.032  TaskA ABORT
10:31:02.050  ALARM
```

のようなトレースが残る。

ここで欲しいのは、

> 「PLC_TIMEOUTがあったからPLCが原因です」

ではありません。

むしろ、

```text
発生事象
   ↓
直接的な異常
   ↓
その異常を引き起こした可能性
   ↓
さらに上流の原因
```

を追跡することです。

# 3. AIに全部やらせない

今回の用途では、次のように分離します。

| 処理                 | 方法               |
| ------------------ | ---------------- |
| timestamp解析        | deterministic    |
| Task ID抽出          | deterministic    |
| Message ID抽出       | deterministic    |
| Function名          | deterministic    |
| Middleware call    | deterministic    |
| 前後関係               | deterministic    |
| Message dependency | deterministic    |
| Data dependency    | deterministic    |
| Timeout判定          | deterministic    |
| 異常コード判定            | deterministic    |
| 原因候補生成             | rule + knowledge |
| 原因候補の意味判定          | **Laya**         |
| 複数原因の優先順位          | **Laya + rule**  |
| 最終判断               | 人間               |

つまり、

> **AIに事実を発見させるのではなく、発見済みの事実を評価させる**

構造です。

これは現在進めているtree-sitterベースのL2解析とも非常に相性がいいです。

```text
request_id
```

# 7. Choice

例えば、

```python
"root_cause_type": {
    "type": "choice",
    "instructions": "What is the most likely root cause category?",
    "criteria": {
        "PLC_COMMUNICATION": "PLC communication failure, timeout, connection problem",
        "MESSAGE_FLOW": "message transmission or reception problem",
        "TASK_LOGIC": "control task internal logic problem",
        "DATA_PROBLEM": "invalid or inconsistent data",
        "TIMING": "timing, scheduling, or race condition",
        "MIDDLEWARE": "middleware or framework problem",
        "UNKNOWN": "insufficient evidence"
    }
}
```

結果が、

```json
{
  "choice": "PLC_COMMUNICATION",
  "probabilities": {
    "PLC_COMMUNICATION": 0.71,
    "MESSAGE_FLOW": 0.13,
    "TASK_LOGIC": 0.08,
    "DATA_PROBLEM": 0.03,
    "TIMING": 0.03,
    "MIDDLEWARE": 0.01,
    "UNKNOWN": 0.01
  }
}
```

となる。

これがJev型の面白いところです。

単に、

```text
原因 = PLC通信
```

ではありません。

**他の可能性も残る。**

# 8. Noul

さらに個別仮説を検証します。

例えば、

```python
"is_plc_timeout_root_cause": {
    "type": "noul",
    "instructions":
        "Does the evidence indicate that the PLC timeout is a root cause "
        "rather than a downstream symptom?"
}
```

別の仮説：

```python
"is_taskb_secondary_failure": {
    "type": "noul",
    "instructions":
        "Is TaskB ERROR likely a secondary failure caused by another upstream event?"
}
```

さらに、

```python
"is_message_delayed": {
    "type": "noul",
    "instructions":
        "Does the trace provide evidence of abnormal message delay?"
}
```

とする。

# 9. Score

そして、

```python
"root_cause_confidence": {
    "type": "score",
    "instructions": "How strongly does the evidence support the root cause hypothesis?",
    "criteria": [
        "very weak",
        "weak",
        "moderate",
        "strong",
        "very strong"
    ]
}
```

とする。

ただし、ここで注意。

**Layaのscoreをそのまま「原因確率」として扱わない**ほうがいいです。

`score`は順序尺度なので、

```text
1 = very weak
2 = weak
3 = moderate
4 = strong
5 = very strong
```

のような「証拠強度」に使うのが適切です。

# 11. さらに重要なのが「反証」

ここまで作ったら、もう一段進めたいです。

例えば、

```text
候補A
PLC通信異常
```

だけを評価するのではなく、

```text
支持する証拠
反証する証拠
```

を分けます。

例えば、

```json
{
  "hypothesis": "PLC communication failure",

  "supporting": [
    "PLC_WRITE occurred",
    "PLC timeout occurred",
    "no response event"
  ],

  "contradicting": [
    "PLC responded successfully 20ms later"
  ]
}
```

これをLayaに渡す。

これによって、

> **最初に見つかったエラーを原因と誤認する**

問題をかなり抑えられます。

# 12. 私なら「時間窓」をかなり重視します

制御サーバーでは、

```text
原因
 ↓
数ms
 ↓
Message
 ↓
数ms
 ↓
Task
 ↓
数十ms
 ↓
Alarm
```

という関係が非常に重要です。

したがって、

```text
T-1000ms ～ T+1000ms
```

だけを見るのではなく、

```text
T-10ms
T-100ms
T-1sec
T-10sec
```

という複数の時間窓を作ります。

例えば、

```text
Event E0 = PLC_TIMEOUT

±10 ms
±100 ms
±1 sec
±10 sec
```

の4層で候補を抽出。

# 13. さらに「トレース＋プログラム」を結合する

ここが、現在のL2 C解析プロジェクトと組み合わせた場合の本命です。

例えばトレースに、

```text
TaskB
 └─ send_plc_command()
       └─ middleware_write()
```

と出たら、プログラム解析DBから、

```text
send_plc_command()
    ↓
middleware_write()
    ↓
PLC driver
```

を引きます。

さらに、

```text
send_plc_command()
    ↓
PLC01
```

だけではなく、

```text
send_plc_command()
    ↓
middleware_write()
    ↓
shared buffer
    ↓
TaskC
```

まで追える。

すると、

```text
TRACE
  +
SOURCE CODE
  +
MESSAGE GRAPH
  +
DATA FLOW
  ↓
TROUBLE GRAPH
```

になります。

これは単なるログ解析よりかなり強力です。

# 18. NanoJevはどこに入れるか

今回の用途なら、

```text
             ┌─ Laya
Decision ────┤
             └─ NanoJev
```

として交換可能にします。

インターフェースを統一：

```python
class DecisionEngine:

    def choice(self, state, question):
        ...

    def noul(self, state, question):
        ...

    def score(self, state, question):
        ...
```

そうして、

```python
engine = LayaEngine()

# later
engine = NanoJevEngine()
```

に交換できるようにする。

NanoJevもChoice/Noul/Scoreを直接確率として扱う設計なので、この抽象化と相性がいいです。([GitHub][3])

# 19. ただし、Layaをそのまま「故障診断AI」とは考えない

ここは重要です。

Layaが返す、

```text
PLC_COMMUNICATION = 0.71
```

は、

> **「PLC通信が真の故障原因であることが71%確定」**

という意味ではありません。

入力したstate、質問、学習済みモデル、校正によって得られた**モデル上の確率・スコア**です。

したがって最終的には、

```text
AI probability
       +
deterministic evidence
       +
program dependency
       +
time correlation
       +
known failure rules
       ↓
investigation priority
```

とするべきです。

```text
                       │

              │ Trace Normalizer │

                       │

              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    Time Graph      Task Graph      Data Graph
        │              │              │
        └──────────────┼──────────────┘
                       ▼
              Evidence Builder
                       │
                       ▼
             Candidate Generator
                       │
              ┌────────▼────────┐
              │ Decision Engine │
              │     Laya        │
              │   / NanoJev     │
              └────────┬────────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Choice         Noul         Score
          │            │            │
          └────────────┼────────────┘
                       ▼
                Root Cause Ranking
                       │
                       ▼
                Investigation UI
                       │
              ┌────────┴────────┐
              ▼                 ▼

```

**この構成なら、現在の `tree-sitter-Project` の解析資産を捨てずに、トレース解析を上に載せられます。**

そして最初の実装対象としては、私は **「1件のトラブルログ → 時系列相関 → 異常イベント候補3～5個 → LayaによるChoice/Noul → HTMLレポート」**までを作るのがよいと考えます。

次の段階で `trace → source function → middleware → message/data flow` を結合すれば、**「この異常が発生したとき、どのC関数・Task・Message・Middlewareまで遡ればよいか」**を自動的に表示する仕組みにできます。
